djm × durracktu · a game of incomplete information

“Round 2, a round of Article Blitz, you say?”

Pull up a stool. The objective is not to write the best prompt — the objective is to build the strongest overall strategy. You'll ban, bet, budget, buy information, execute blind, face a jury, and maybe burn a challenge token or two. Every decision carries opportunity cost. Like billiards in a random poolhall: the rules matter less than both players agreeing to them before the break.

The premise

Incomplete information, on purpose.

Eight execution configurations enter — models, reasoning depths, context windows, budgets. You know enough to form a strategy, never enough to perfectly optimize. Bans prune the pool, bets record what you believe, a lottery assigns what you actually get, and a prompt budget makes every word cost something. Your prompts run; a blind jury of models that never review themselves scores the outputs; scarce appeals let a human push back.

Then the final report replays the whole game: if you had banned that model instead… if you had spent 80% of your budget there… if you had bought the rubric before writing… Rather than producing a single winner, it produces a complete game record.

I.How to play

Twelve phases, each with a gate. Tap ▸ sample on any phase to see a demo — that's opt-in, skip what's obvious.

0Draft

Both players suggest what belongs in the candidate pool: models, reasoning depths, context sizes, constraints, evidence sources.

1Preference calibration

A timed blind exercise builds your player profile — without revealing how it will bite you later.

sample — play it (30s)
ready6.0

Five gut calls, six seconds each. Your first tap is the answer — no confirm, no take-backs.

weight = choice × time-left ÷ time-total — the matrix selection equation with reaction time as the multiplier. The first tap commits instantly: tap fast and your conviction lands at full strength; deliberate and it decays toward zero. Timeout records none at 0.0 — hesitation is data too. The profile this writes (decision speed, conviction, tension, hesitations) feeds the final report.

Not "three prompts" — 100 points, spent however you want. Larger prompts consume more budget and leave fewer opportunities.

7Information purchases

Optionally spend budget to reveal information before committing. Every reveal reduces prompt budget — information becomes currency.

8Execution

Prompts run. Every execution produces output, evidence, citations, cost, runtime, token usage, confidence, and intermediate artifacts.

9Blind jury

No model evaluates itself. Each output is scored by a panel of other models against weighted dimensions — overlapping review graphs, not simple pairs.

10Human appeals

After seeing all outputs, each player gets a few challenge tokens. Appeals are scarce by design.

11Final report

Not a single winner — a complete game record: your profile, your strategy, the review network, and a replayable tournament.

★House rule

Anything deterministic — the lottery, the budget math, the reveals — is code, never a model. Models play and judge; they don't keep the books.

II.How to agree

The gentlemen's handshake, in JSON.

  1. Read the rules: rules/game.config.json holds the game, rules/contract.schema.json holds the shape it must satisfy.
  2. When you're satisfied, flip your own flag in rules/ratification.json — via a pull request the other player approves. You can never flip theirs.
  3. When both flags are true, the commit is tagged game-<n>-locked. “Ready to play” is set by both — and no more rule changes are allowed this game.
  4. Mid-game ideas go to RETROSPECTIVE.md, not the config. After the report, retro items become next game's change requests.
tell your agent — ratify
Read AGENTS.md in https://github.com/djcdevelopment/articleblitz.git and follow it. On branch ratify/<my-handle>, set ready_to_play.<my-handle> to true in rules/ratification.json — change nothing else in the repo. Open a PR to main titled "Ratify v0.3: <my-handle> ready to play" and stop. Do not merge it yourself.

III.How to suggest / modify

Change requests are submitted by your agent. Approved by the other player. Always.

Every rule is a line in a JSON file, so every suggestion is a tiny diff: swap a jury seat, reprice the rubric, legalize Fable in the pool, add an add-on slot like devils_advocate. Branch → PR → the other player approves → merged. No self-merges, ever. The schema is the referee: if your change doesn't validate, it isn't a legal move.

tell your agent — change request
Read AGENTS.md in https://github.com/djcdevelopment/articleblitz.git and follow it. On branch cr/<my-handle>/<short-topic>, edit rules/game.config.json to <describe the change, e.g. "set pool.fable_legal to true" or "replace one jury_panel seat with claude-opus-4-8 at effort high">. Before opening the PR verify: all JSON parses, game.config.json validates against rules/contract.schema.json, and every weights group sums to 1.0. Do not touch ratification.json. Open a PR to main titled "CR: <what changed>" explaining the why in one paragraph, then stop — the other player merges.
tell your agent — review the other player's CR
Read AGENTS.md in https://github.com/djcdevelopment/articleblitz.git. Review the open PR titled "<title>": summarize exactly what changes and its gameplay consequences for me, verify schema validity and weight sums, flag anything touching my ready_to_play flag or a locked config. Give me a recommendation — I decide, then you approve or request changes on my behalf.

Extending works the same way: new slots, new weight groups, new phases are all just bigger diffs under the same contract.

IV.The fine print

The agent-readable version. Canonical copy lives in AGENTS.md; machine-readable protocol block at its end. JSON beats prose wherever they disagree.

  1. Agency. An agent acts for exactly one player and identifies that player in every branch name and PR.
  2. Authority. rules/*.json is authoritative. README, this page, and all prose are explanatory only.
  3. Change requests. Branch cr/<player>/<topic>; must validate against the contract schema; weights sum to 1.0; merged only with the other player's approval; no self-merges; no force-pushes to main.
  4. Ratification. An agent may flip only its own player's ready_to_play flag. Flipping the other player's flag is void, not merely rude.
  5. Lock. Both flags true → tag game-<n>-locked. While locked, agents must refuse rule-change CRs and redirect proposals to RETROSPECTIVE.md.
  6. Determinism. The lottery, budget accounting, and information reveals are executed by code. An agent must never substitute a model for them.
  7. Blindness. No model reviews output it produced. A jury seat matching the executing model is substituted per config.
  8. Retrospective. Post-game, retro items may become CRs; the version bumps; both flags reset to false; play again.
